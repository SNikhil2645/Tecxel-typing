## 1. Overview

TECXEL Typing Championship is a browser-based competition where registered participants type through 3 rounds of increasing difficulty. Every participant plays all 3 rounds (no elimination). Final ranking is determined by averaging round scores, each weighted 50% speed / 50% accuracy.

| Parameter | Value |
|-----------|-------|
| Rounds | 3 (Sprinter → Precisionist → Typing Master) |
| Time per round | 2 minutes (fixed) |
| Difficulty progression | Easy → Punctuation → Numbers + Symbols |
| Concurrent users | ~50 |
| Scoring | Server-authoritative (client never trusted) |
| Elimination | None |

## 2. Tech Stack & Why

| Layer | Choice | Reason |
|-------|--------|--------|
| Frontend | React 18 + Vite | Fast HMR, small bundles, code-splitting out of the box |
| Styling | CSS Variables (no framework) | Full control over TECXEL's custom pixel/blocky aesthetic |
| Backend | Node.js + Express | Shared JS with frontend, lightweight for this scale |
| Database | MongoDB + Mongoose | Flexible schema, fast reads, Atlas for reliability |
| Auth | JWT (localStorage) | Stateless, no server session overhead |
| Deployment | Vercel (FE) + Render (BE) or local network | Free tier handles 50 users easily |

**Why not Tailwind?** The TECXEL poster has a very specific pixel-blocky, circuit-trace, ribbon-divider aesthetic. CSS variables + custom styles give precise control. Tailwind would fight the design language.

**Why not WebSocket?** REST is sufficient for 50 users. Leaderboard refreshes via polling (every 10s) or manual refresh. WebSocket adds complexity without proportional benefit at this scale.

## 4. Architecture

```
┌─────────────────────┐
│   React Frontend    │  Vite dev server / static build
│   (Vite + React)    │
└────────┬────────────┘
         │  REST API (JSON)
         │  Authorization: Bearer <JWT>
┌────────▼────────────┐
│   Express Backend   │  Node.js process
│   (REST API)        │
└────────┬────────────┘
         │  Mongoose ODM
┌────────▼────────────┐
│   MongoDB           │  Atlas cluster or local
│   (3 collections)   │
└─────────────────────┘
```

**Data flow for score submission:**
1. Client captures typed text + timestamps locally
2. Client sends `{ round, typedText, targetText, startTime, endTime }` to server
3. Server independently calculates WPM, accuracy, errors, score
4. Server stores result, returns computed values to client
5. Client displays server-returned values (never its own calculations)

## 5. User Journey

```
Home
  → Register (name, roll, course, year, section, email, password)
  → Receive Participant ID (TCX-001)
  → Login (participantId + password)
  → Rules page (rounds overview, scoring explanation)
  → Round 1 — The Sprinter (easy, 2 min)
  → Round 1 Result (WPM, accuracy, errors, score)
  → Round 2 — The Precisionist (punctuation, 2 min)
  → Round 2 Result
  → Round 3 — The Typing Master (numbers/symbols, 2 min)
  → Round 3 Result
  → Final Result (average score, rank)
  → Leaderboard (live-sorted)
```

**Constraints:**
- No elimination — every participant plays all 3 rounds
- One attempt per round — once completed, cannot restart
- Must complete rounds in order (1 → 2 → 3)

## 7. Database Schema

### 7.1 participants

```javascript
{
  _id: ObjectId,
  name: { type: String, required: true, trim: true },
  rollNumber: { type: String, required: true, unique: true },
  course: { type: String, required: true },       // B.Tech, BCA, MCA, etc.
  year: { type: Number, required: true, min: 1, max: 5 },
  section: { type: String, required: true },       // A, B, C, etc.
  email: { type: String, required: true, unique: true, lowercase: true },
  phone: { type: String },                         // optional
  password: { type: String, required: true },      // bcrypt hashed
  participantId: { type: String, required: true, unique: true },  // TCX-001
  registeredAt: { type: Date, default: Date.now },
  isActive: { type: Boolean, default: true },
  isDisqualified: { type: Boolean, default: false }
}
```

**Indexes:** `participantId` (unique), `email` (unique), `rollNumber` (unique)

### 7.2 passages

```javascript
{
  _id: ObjectId,
  round: { type: Number, required: true, enum: [1, 2, 3] },
  title: { type: String, required: true },
  content: { type: String, required: true },        // the typing text
  difficulty: { type: String, enum: ['easy', 'medium', 'hard'] },
  characterCount: { type: Number },                  // computed on save
  isActive: { type: Boolean, default: true },
  createdAt: { type: Date, default: Date.now }
}
```

**Indexes:** `{ round: 1, isActive: 1 }`

**Seed requirement:** Minimum 10 passages per round to prevent memorization. Randomly assign one per attempt.

### 7.3 results

```javascript
{
  _id: ObjectId,
  participantId: { type: String, required: true },   // ref → participants
  round: { type: Number, required: true, enum: [1, 2, 3] },
  typedText: { type: String, required: true },        // full typed content
  targetText: { type: String, required: true },       // passage at attempt time
  correctCharacters: { type: Number, required: true },
  totalCharacters: { type: Number, required: true },
  errors: { type: Number, required: true },
  wpm: { type: Number, required: true },              // server-computed
  accuracy: { type: Number, required: true },         // server-computed, 0-100
  speedScore: { type: Number, required: true },       // server-computed, 0-100
  roundScore: { type: Number, required: true },       // server-computed, 0-100
  finalScore: { type: Number },                       // set after round 3

  startTime: { type: Date, required: true },
  endTime: { type: Date, required: true },
  duration: { type: Number, required: true },         // seconds
  completedAt: { type: Date, default: Date.now }

```

**Indexes:** `{ participantId: 1, round: 1 }` (unique compound — one attempt per round), `finalScore: -1` (leaderboard sort)

## 8. API Reference

### 8.1 Authentication

| Method | Endpoint | Body | Response | Status |
|--------|----------|------|----------|--------|
| POST | `/api/auth/register` | `{name, rollNumber, course, year, section, email, phone?, password}` | `{participantId, token}` | 201 |
| POST | `/api/auth/login` | `{participantId, password}` | `{token, participant}` | 200 |
| POST | `/api/auth/admin/login` | `{email, password}` | `{token}` | 200 |

**Errors:**
- 400: Validation failed (missing/invalid fields)
- 409: Duplicate email, roll number, or participant ID
- 401: Invalid credentials

### 8.2 Competition

| Method | Endpoint | Auth | Response | Status |
|--------|----------|------|----------|--------|
| GET | `/api/competition/round/:round` | JWT | `{passage: {_id, title, content}, round, totalPassages}` | 200 |
| GET | `/api/competition/status` | JWT | `{roundsCompleted: [1,2], currentRound: 3, allDone: false}` | 200 |

**Errors:**
- 401: No/invalid token
- 403: Round not yet available (must complete previous rounds)
- 409: Round already completed

### 8.3 Results

| Method | Endpoint | Auth | Body | Response | Status |
|--------|----------|------|------|----------|--------|
| POST | `/api/results/submit` | JWT | `{round, typedText, startTime, endTime}` | `{wpm, accuracy, errors, speedScore, roundScore}` | 201 |
| GET | `/api/results/my-results` | JWT | — | `{rounds: [{round, wpm, accuracy, errors, roundScore}...], finalScore}` | 200 |

**Server-side recalculation on POST:**
1. Verify round hasn't been completed (409 if yes)
2. Fetch passage from DB (don't trust client's targetText)
3. Character-by-character comparison
4. Compute: correctCharacters, totalCharacters, errors, WPM, accuracy, speedScore, roundScore
5. If round 3: compute finalScore = average of all 3 rounds
6. Store in DB, return server-computed values

**Errors:**
- 400: Invalid input (missing fields, invalid round number)
- 409: Round already completed
- 500: Server error

### 8.4 Leaderboard

| Method | Endpoint | Auth | Response | Status |
|--------|----------|------|----------|--------|
| GET | `/api/leaderboard` | No | `[{rank, participantId, name, course, finalScore, rounds: [{round, wpm, accuracy, roundScore}...]}]` | 200 |

Sorted by `finalScore` descending. Only includes participants who completed all 3 rounds.

## 9. Typing Engine

### 9.1 Core Component

The typing engine is a single reusable component used across all 3 rounds. Only the passage content changes.

```
┌─────────────────────────────────────────┐
│  TARGET TEXT (display only)             │
│  ██████████████████████████████████████ │
│  Characters: correct=blue, wrong=red,   │
│  pending=gray, cursor=blue block        │
├─────────────────────────────────────────┤
│  TYPING INPUT (user types here)         │
│  [textarea — paste disabled,            │
│   context menu disabled]                │
├─────────────────────────────────────────┤
│  LIVE STATS                            │
│  WPM: 72  │  Accuracy: 98%  │  ERR: 14 │
├─────────────────────────────────────────┤
│  TIMER                                 │
│  ████████████░░░░░░  1:23              │
└─────────────────────────────────────────┘
```

### 9.2 Behavior

1. On round start: show 3-2-1-GO countdown (3 seconds)
2. Timer starts at 2:00, counts down to 0:00
3. On each keystroke: compare input to target, update highlighting
4. On timer expiry: auto-submit current progress
5. On submit: send to server, show loading, display server-returned results
6. Disable input after submission

### 9.3 Character States

| State | Color | Condition |
|-------|-------|-----------|
| Correct | `--color-accent` (#3B5BFF) | Input char === target char |
| Incorrect | `--color-error` (#D32F2F) | Input char !== target char |
| Pending | `--color-ink` light opacity | Not yet typed |
| Current | Blue block cursor | Next character to type |

### 9.4 Anti-Paste Measures

```javascript
// Block paste
textarea.addEventListener('paste', (e) => e.preventDefault());

// Block context menu
textarea.addEventListener('contextmenu', (e) => e.preventDefault());

// Block Ctrl+V / Cmd+V
textarea.addEventListener('keydown', (e) => {
  if ((e.ctrlKey || e.metaKey) && e.key === 'v') e.preventDefault();
});
```

## 10. Scoring System

### 10.1 WPM Calculation

```
Gross WPM = (correctCharacters / 5) / minutesElapsed
```

Example: 720 correct characters in 2 minutes → 720/5/2 = **72 WPM**

### 10.2 Accuracy

```
Accuracy = (correctCharacters / totalTypedCharacters) × 100
```

Example: 706 correct / 720 typed → **98.06%**

### 10.3 Speed Score (normalized to 0-100)

```
Speed Score = min((WPM / 100) × 100, 100)
```

Benchmark: 100 WPM = 100 speed score. Capped at 100.

### 10.4 Round Score

```
Round Score = (Speed Score × 0.5) + (Accuracy Score × 0.5)
```

### 10.5 Final Score

```
Final Score = (Round1 Score + Round2 Score + Round3 Score) / 3
```

### 10.6 Worked Example

| Round | WPM | Accuracy | Speed Score | Round Score |
|-------|-----|----------|-------------|-------------|
| 1 (Sprinter) | 80 | 98% | 80 | (80×0.5)+(98×0.5) = **89** |
| 2 (Precisionist) | 72 | 96% | 72 | (72×0.5)+(96×0.5) = **84** |
| 3 (Typing Master) | 65 | 94% | 65 | (65×0.5)+(94×0.5) = **79.5** |

**Final Score = (89 + 84 + 79.5) / 3 = 84.17**

### 10.7 Important Notes

- Display actual WPM uncapped even at 115+ — only the speed score component caps at 100
- Show WPM, Accuracy, Errors, Round Score, and Final Score separately on result screens
- Speed benchmark (100 WPM) is a scoring reference, not a display cap
- Server is the source of truth for all scores — always

## 11. Anti-Cheating

### 11.1 Client-Side Measures

| Measure | Implementation |
|---------|----------------|
| Paste block | `onPaste` preventDefault + block Ctrl+V/Cmd+V + disable context menu |
| Tab switch detection | `visibilitychange` event → increment counter, warn at 3, disqualify at 5 |
| Fullscreen | `requestFullscreen()` before round starts; detect exit → warn |
| One-attempt lock | Check results collection before allowing round start; reject if completed |
| Input sanitization | Strip HTML/scripts from typed text before sending to server |

### 11.2 Server-Side Measures (Critical)

| Measure | Implementation |
|---------|----------------|
| Score recalculation | Server recomputes WPM, accuracy, errors, score from raw typedText + targetText |
| Passage verification | Server fetches passage from DB — never trusts client-submitted targetText |
| Duplicate prevention | Compound unique index on `{participantId, round}` — rejects second submission |
| Timestamp validation | Server checks duration is reasonable (90-150 seconds for a 2-minute round) |
| Rate limiting | Limit result submissions to 1 per 30 seconds per user |

### 11.3 What Client Sends

```json
{
  "round": 1,
  "typedText": "the quick brown fox jumped over...",
  "startTime": "2026-09-08T10:05:00.000Z",
  "endTime": "2026-09-08T10:07:00.000Z"
}
```

### 11.4 What Server Does

1. Verify JWT → extract participantId
2. Check round hasn't been completed → reject if yes
3. Fetch passage from DB by round number
4. Character-by-character comparison
5. Compute all metrics server-side
6. Store result
7. If round 3: compute finalScore, update all results with final score
8. Return server-computed values to client

**Never trust the client. The frontend displays live WPM for UX, but the server is always the authority.**

## 15. Performance for 50 Users

### 15.1 Database Optimization

| Collection | Index | Purpose |
|------------|-------|---------|
| participants | `participantId` (unique) | Fast login lookup |
| participants | `email` (unique) | Fast registration check |
| passages | `{ round: 1, isActive: 1 }` | Fast passage fetch per round |
| results | `{ participantId: 1, round: 1 }` (unique) | One-attempt check + submission |
| results | `{ finalScore: -1 }` | Fast leaderboard sort |

### 15.2 Application Optimization

| Concern | Solution |
|---------|----------|
| Passage caching | Cache active passages in server memory (Map/Object); invalidate on admin edit |
| Connection pooling | Mongoose default pooling (5-10 connections) handles 50 users easily |
| Leaderboard query | Pre-computed `finalScore` field; single indexed sort query |
| Rate limiting | `express-rate-limit`: 100 requests/min per user; 1 submit/30s |
| Response compression | `compression` middleware for gzip responses |
| JWT verification | Stateless — no session store overhead |

### 15.3 Load Estimate

- 50 concurrent users × ~2 requests/min average = 100 req/min
- Each request: <50ms response time with proper indexing
- MongoDB: handles 1000+ reads/sec easily
- **No special scaling needed at this scale**

## 21. Risks & Mitigations

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| MongoDB connection failure during event | High | Low | Atlas replica set + local backup |
| 50 concurrent users overwhelming server | Medium | Medium | Proper indexing, connection pooling, rate limiting |
| Score tampering via devtools | High | High | Server recalculates everything; never trust client |
| Browser incompatibility | Medium | Medium | Test on Chrome, Edge, Firefox before event |
| Timer desync due to network latency | Medium | Low | Sync with server timestamp; client handles local countdown |
| Passage leaked before round | High | Low | Fetch only when authenticated + round starts |
| Admin panel unauthorized access | High | Low | Separate admin JWT; strong password |
| Data loss (results not saved) | High | Low | Auto-save to localStorage; retry failed submissions |
| Deployment failure on event day | High | Medium | Test 3 days before; keep local backup running |
| Participant forgets ID/password | Low | Medium | Admin can view all participants; manual lookup |

## Key Decisions

| Decision | Rationale |
|----------|-----------|
| Vite over Create React App | Faster dev server, smaller bundles, better DX |
| JWT over sessions | Stateless; no server session store; scales easily |
| Server-side scoring | Critical — client can be manipulated; server is authority |
| MongoDB Atlas over local | Reliability, automatic backups, no local setup hassle |
| CSS variables over Tailwind | Full control over TECXEL's custom pixel-blocky aesthetic |
| REST over WebSocket | Sufficient for 50 users; WebSocket adds unnecessary complexity |
| Single TypingEngine component | Reusable across all 3 rounds; only content/difficulty changes |
| No elimination | Every registered participant plays all 3 rounds; fairer competition |
